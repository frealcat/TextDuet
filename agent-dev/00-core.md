# 00 Core Rules

本文件定义每次任务都适用的项目基线、上下文和工具规则。与 `AGENT_DEV.md`、`10-runtime-contracts.md` 一起必读。

## 1. 项目基线

- 正式名称：TextDuet；建议仓库名和 npm package name：`textduet`。
- 许可证：Apache-2.0；根目录 `LICENSE` 与 `NOTICE` 是发布物的一部分。
- 平台：首版只支持 Chrome Manifest V3，不承诺 Edge、Firefox 或 Safari。
- 技术栈：WXT、React、TypeScript strict、Vitest、Zod Mini、Radix UI、Lucide React、npm、Node.js 22+。
- 框架边界：禁止引入 Next.js 或依赖 Next.js 运行时、路由、SSR、Server Components 的方案；浏览器扩展入口统一由 WXT 管理。
- 产品模式：本地优先、BYOK、无项目中转服务器、无插件订阅费；模型 API 费用由用户承担。
- M1 必须包含成本预估、每日用量账本和预算提醒。

UI 依赖采用渐进策略：Radix 只用于 Popup/Options 中难以可靠手写的交互原语，Lucide 只按图标导入；Translator Script 不得引入 UI 组件库。React Hook Form 延后到 M1 表单复杂度确有需要时再评估。

任何与这些基线冲突的改动都属于产品决策，必须先获得用户明确授权并同步 PRD。

## 2. 任务开始检查

每次任务开始必须：

1. 确认当前工作目录和仓库根目录。
2. 运行 `git status --short`，识别用户已有修改和未跟踪文件。
3. 阅读任务相关的入口、类型、测试、文档和 package scripts。
4. 确认任务是分析、诊断、实现、审查、发布准备还是等待；不要把只读请求扩大成修改。
5. 写下明确的完成条件；复杂任务使用分步计划并保持最多一个进行中步骤。

不得假设工作树干净。遇到重叠修改时保留用户内容，无法安全合并才请求用户处理。

## 3. 上下文与执行账本

执行账本不要求写入仓库，但在长任务中必须可恢复。它至少包含：

- 用户目标、授权范围和不能做的事。
- 当前计划步骤与完成状态。
- 活动文件和关键符号。
- 已确认的安全、产品与架构决策。
- 最新失败、原始错误和已尝试方案。
- 已运行验证及结果。
- 精确下一步。

上下文压缩或任务恢复后，先读取账本、`git status` 和活动 diff；不要凭记忆重做或覆盖已完成修改。

## 4. 工具与风险分级

### 可直接执行

- 仓库内读取、搜索、diff、历史查看和静态分析。
- 已有脚本的 typecheck、单元测试、构建和无副作用的检查。
- 用户已授权范围内的局部文件修改。
- 为当前任务访问官方文档或公开资料的只读检索。

### 先确认

- 安装或升级依赖，修改 package manager、锁文件策略或构建平台。
- 网络写入、外部账号操作、Issue/PR/评论、上传、部署和发布。
- Git commit、push、rebase、force 操作或改变远程仓库。
- 修改仓库外文件、系统配置、浏览器个人数据或真实 API 账户。
- Manifest 权限、用户数据范围、密钥策略、遥测和费用默认值变化。

### 禁止

- 破坏性 Git 操作、丢弃未提交修改或覆盖未知文件。
- 输出或持久化秘密，使用真实 Key 进入测试、日志或构建产物。
- 绕过安全控制、付费墙、验证码或网站访问限制。
- 未授权的外部消息、发布、数据采集或自动化账户行为。

## 5. 变更原则

- 采用完成目标的最小可靠改动；不要顺手重构无关代码。
- 优先修复根因，避免只遮蔽错误或放宽安全校验。
- 复用项目现有依赖和模式；新依赖必须说明必要性、体积、权限、许可证和替代方案。
- 源码、测试和文档共同构成产品；契约变化必须同步更新。
- 生成物 `.output/` 不提交，除非未来发布流程明确规定。
- 不把个人机器路径、Key、账号或临时调试数据写入仓库。

## 6. 沟通要求

- 先报告结果和影响，再说明过程。
- 明确区分“已验证”“基于代码推断”“尚未验证”。
- 风险和阻塞必须给出证据、已尝试方案和所需用户决策。
- 不以篇幅代替准确性，不以自信措辞代替验证。
