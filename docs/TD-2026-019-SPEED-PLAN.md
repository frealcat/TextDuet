# TD-2026-019 翻译速度优化方案

## 当前瓶颈

1. 首次翻译在发送 Provider 请求前要等待全部批次的成本预估完成，形成额外瀑布等待。
2. 4000 字符大批次虽然减少请求数，但模型需要更久才能输出完整 JSON；首段可见时间被整批首 token 时间和结构化输出延后。
3. 流式段落解析只有在模型输出完整的 `TranslatedBlock` 对象后才能安全渲染，不能把半截译文写入网页。
4. 动态页面继续进入后续批次，不能追加到已经发送的 HTTP 请求，因此需要缩短每批闭环时间。

## 本轮已落地

- 首批字符上限约 1200，优先让第一个完整段落尽快返回；后续批次恢复 4000 字符上限，控制请求数量。
- 成本预估与首个 Provider 请求并行，不再阻塞首段渲染；估算失败只影响成本摘要，不阻塞翻译。
- SSE 事件按 chunk 增量读取，完整段落对象通过 schema、ID 集合和重复 ID 校验后立即渲染。
- 普通 JSON 在同一次响应中 fallback，不进行第二次请求。
- 本地缓存命中段落先逐段发回；动态新增内容在当前批次结束后立即排队。

## 推荐的下一阶段优化

### P0：用真实 Qwen 流测量首段时间

记录四个时间点：候选提取完成、请求发出、首个 SSE data、首个译文 DOM 插入。分别对 20 段、70 段和动态页面测量，目标是首段 DOM 插入时间低于整批完成时间的 50%。

### P1：Provider 能力协商

对已知支持结构化输出的模型增加可选 `response_format`；对不支持的端点保持当前 JSON 提示词。不得为了兼容性自动重试第二次。

### P1：首屏优先队列

在候选收集后按 viewport 可见性排序，首批优先当前视口和标题/首段；视口外内容按文档顺序进入后续批次。这样首段可见时间与页面总长度解耦。

### P2：请求级吞吐调优

在用户明确允许的前提下，对不同批次做有限并发（默认 1，最多 2），并保持每个标签页可停止、成本按响应 usage 结算；未经实测不默认开启，避免触发限流和增加账单峰值。

## 验收指标

- 首个译文 DOM 插入早于 `TRANSLATION_COMPLETE` 事件。
- 20 段普通页面：首段出现时间、整页完成时间、请求数和 token 用量均有记录。
- 70 段动态页面：首屏段落优先出现，滚动加载内容进入后续批次。
- 停止后不再插入新译文、不发起新批次。
- 失败或断流时不缓存不完整批次，可靠 usage 仍能入账。
